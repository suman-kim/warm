현재: API만 있고 화면이 없다.
- 기사 심사: GET /admin/drivers(?status=PENDING), GET /admin/drivers/:id(신청자·서류 상태), GET …/documents/:type/file, PATCH approve, PATCH reject(사유 + 반려할 서류)
- 공지: POST /admin/notices(대상: 전체·고객·기사), DELETE /admin/notices/:id
- 약관: POST /admin/legal-documents(종류·판 번호·시행일 — 새 판으로 올리고 지난 판은 남긴다)
주문·회원 관리 API는 없다. 약관은 운영자가 올리기 전에는 앱의 약관 화면이 비어 있다 — 출시 전에 이용약관·개인정보 처리방침을 올려야 한다 (→ 작업 31).
범위: 기사 심사(서류 보기 포함), 공지·약관 관리, 주문 현황 조회, 회원 정지. 운영에서는 CORS_ORIGINS에 이 웹의 주소를 넣는다.
[2026-10-13] 화면 디자인은 사용자가 준다 — 디자인을 받기 전에는 화면을 만들지 않는다. 디자인에 주문 현황·회원 정지처럼 API가 없는 화면이 있으면 API부터 추가한다. 그때까지 개발·테스트의 기사 승인은 backend/tool/approve-drivers.sh(서류를 보지 않고 대기 중인 기사를 모두 승인).
[2026-10-13] 디자인을 받았다: design/MOVO Admin.dc.html (움직이는 프로토타입 하나 — 로그인, 기사 심사 목록·상세, 주문 현황, 회원, 정산, 공지사항, 약관·정책, 관리자 계정 + 대화상자 12개).
디자인이 정한 것: 권한 3종(최고 관리자=전부, 운영 관리자=심사·주문·회원·공지·약관, 정산 담당=주문·정산), 관리자는 초대 메일로 추가, 회원 정지 7일·30일·무기한(진행 중인 배송이 있으면 불가), 정산은 월~일 한 주를 모아 화요일 지급·수수료 10%, 약관 5종(기사 운송 약관 포함).
디자인의 'API 추가 필요' 표시: 주문 현황, 회원, 정산, 관리자 계정 — 서버에 API를 먼저 추가한다.
디자인에 있지만 받는 값이 없는 것: 기사 생년월일, 차량 연식(앱이 받지 않는다), 서류 쪽수, 주문번호(MV+날짜+순번). 초대받은 관리자가 비밀번호를 정하는 화면은 디자인에 없다.
폴더: admin-web/ (React + Vite + TypeScript + Tailwind). 디자인을 다시 볼 때: 템플릿은 <x-dc> 안, 동작과 예시 데이터는 그 뒤의 script.
